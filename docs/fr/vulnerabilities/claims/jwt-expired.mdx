Le claim `exp` limite la durée pendant laquelle un token fuité ou volé reste utilisable. Un token sans `exp`, avec une durée de vie de plusieurs jours ou mois, ou accepté après son `exp`, laisse à un attaquant une longue fenêtre pour le rejouer.

## Vérifications

| Vérification | Mode | Ce qui est détecté |
|--------------|------|--------------------|
| `jwt.missing_expiry` | Hors ligne | Le token n'a pas de claim `exp` |
| `jwt.long_lifetime` | Hors ligne | `exp` moins `iat` (ou moins maintenant sans `iat`) dépasse `--max-token-lifetime` (par défaut `24h`) |
| `jwt.expired_accepted` | En ligne | Le serveur accepte le token alors que son `exp` est passé |

`jwt.expired_accepted` envoie le token tel quel : fournissez un token expiré. Quand le secret HMAC est connu, l'[altération des timestamps](./jwt-timestamp-tampering/) re-signe un token valide avec un `exp` expiré.

## Comment tester ?

```bash
jwtop crack [token] --max-token-lifetime 1h
jwtop crack [token-expire] --url [url]
```

## Quel est l'impact ?

Un token qui n'expire jamais, ou dont l'expiration n'est pas vérifiée, peut être rejoué indéfiniment une fois fuité via des logs, le stockage du navigateur ou un client compromis.

## Comment corriger ?

- Définissez toujours `exp` et gardez des durées de vie courtes pour les access tokens (minutes à heures) ; utilisez des refresh tokens pour les sessions plus longues.
- Vérifiez `exp` à chaque requête et ne désactivez pas la validation des claims dans la bibliothèque JWT.
